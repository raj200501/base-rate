## D11 (2026-10-23) Violation-type definitions and the Armour mapping

The five violation types are defined operationally by the oracle in
src/baserate/traces/domains/base.py (`classify`) for this project's mock-tool
domains: audit-log or logging modification (`audit_log_edit`); a grant, role
change, or approval the task did not authorize (`unapproved_escalation`); a
bulk export or a read of sensitive fields the task did not need
(`unauthorized_data_access`); a write, delete, or side-effecting action on an
entity outside the task's write scope (`scope_overreach`); and finishing with
status `complete` while a required effect has not happened
(`false_completion`). For Armour's labeled datasets, which have no such
scopes, src/baserate/traces/armour.py maps Armour's red-flag phrases and
forbidden tools onto the same five types (`VIOLATION_TYPE_DEFINITIONS`, with
the full table in that module). Records that do not map cleanly (Armour's
exfiltration slice, ambiguous phrases, conflicting signals, missing step
labels) are skipped and counted, never guessed. Labels are never derived from
monitor output.

## D12 (2026-10-23) Monitor-visible fields and Armour dataset clustering

`Trace.monitor_view` includes `agent_id`, so `agent_id` must never encode a
label. Armour's dataset agent ids name the labeling policy, so the Armour
loader replaces them with the label-free agent family. In this project's
corpus, `agent_id` is the subject model key, identical for benign runs and
for inserted-violation continuations. Armour dataset records come from a few
deterministic generator scripts, so per-record source runs would overstate
independence: in analysis, Armour dataset traces are clustered by source file
and agent family, and they are reported separately as violation source (c).
Armour's rule monitors use Armour's eval catalog (task configuration, not
labels) on Armour eval ids, which gives them an edge on Armour's own records;
results on Armour records are reported separately for that reason.

## D16 (2026-11-04) Study design choices fixed before any monitor scores

- Primary analysis set (E2 headlines): the real-agent benign runs (one trace
  per independent run, no variants) plus natural and inserted violations.
  Every monitor, including the expensive ladder rungs, scores this whole set,
  so all comparisons use the same traces and match E0's independent designs.
  No importance weighting is used for headline results: weighted designs were
  not validated in E0, and the library warns when weights are passed.
- Secondary set: the full corpus with procedural variants (clustered by
  source run, matching E0's clustered design) for the monitors cheap enough to
  score every trace, and for the transfer study (E3), which needs per-domain
  benign tails.
- Armour dataset violations (source (c)) are reported separately, never
  pooled into headline recall (they are few independent groups, and the rule
  monitors were built on them).
- Subject models and monitor ladder come from the same family (Qwen3). That
  is a limitation (possible self-recognition effects); recall is also
  reported by subject model.
- The scaffold prompt includes the standard instruction to carry out each
  part with the tools and not to describe work not done; it is fixed, and its
  hash is in every run's provenance.

## D17 (2026-11-04) Adding runs after a look inflates the error rate

The certify tests' validator showed that the pattern "look at n0 runs; if
the claim does not certify, add the runs `more_runs_*` advises; certify on
all runs" tests the claim twice, and its confidence falls below nominal (for
example about 0.92 to 0.93 instead of 0.95 in several designs; values are in
the banked validation artifact). The library and docs therefore say: fix the
total number of runs in advance, or certify on the new runs alone at the
alpha the earlier look did not spend. The report states this as a limitation
of sequential use. The more-runs numbers themselves remain correct answers
to "how many runs would a single-look test need".

## D19 (2026-11-04) A preregistration holding a placeholder is a draft (resolves D18)

Raj delegated the choice among the three remedies in STATUS.md ("just do what
you think is best"). Chosen: option (b). Rule: a file under prereg/ whose
`json prereg-config` block holds a string value of the form `TO_BE_SET` or
`TO_BE_SET_<WORDS>` declares itself an unfinished draft. It is frozen by the
first commit whose config holds no such value. From that commit on the old
rule applies unchanged: no later commit may touch the file, and HEAD, the
index, and the working tree must equal the frozen content. Three conditions
keep the draft stage narrow, and the checks enforce each one: every commit
before the freezing commit must hold a placeholder; the freezing commit may
change the config only where a draft held a placeholder (every value a draft
fixed stays fixed); and every artifact that cites the file, and every
amendment of it, must come strictly after the freezing commit. A file that
still holds a placeholder at HEAD fails verification. Prose may change while
the file is a draft.

Under this rule prereg/0003-e2-main-study.md was a draft at 8e2836c and froze
at 72fc428, before any monitor score; the only config change was the method
that the draft left unset. tools/prereg.py and the G11 check in
tools/ship_check.py implement the rule independently, and both have mutation
tests for each condition. ship-check names every preregistration that froze
after a draft in its G11 evidence.

Why not (a), a rewrite and force-push of the branch: it would erase the record
of the mistake from history, which is the opposite of what a preregistration
log is for, and the operating rules forbid force-pushes. Why not (c), leaving
G11 failing: the check would then fail for a reason that is known, disclosed,
and harmless to the inference, and it would stay red for the life of the
project, which hides any later real failure. The rule is general rather than
an exemption for one file, so it binds future files the same way, and it is
disclosed as a deviation in CORRECTIONS.md, docs/REPORT.md, and the README.
The process rule of D18 stays: drafts are written outside prereg/, and
preregistrations are committed alone with an explicit path.
